## 一、本阶段做了什么

1. **固定基线**：确定模型、量化、运行器、构建参数与功耗模式，写入 `tools/serve_llama.sh`，所有测量都在同一条命令与同一目标板上完成。
2. **目标板实测**：内存（整栈 RSS/HWM）、冷加载、热聊首声、单图/读字/比较时延、插话停声、取消后重试。
3. **按瓶颈只改一个变量**：
   - 变量 A：llama-server 并行槽位 4 → 1（`--parallel 1`）；
   - 变量 B：批大小 `--batch-size 256 --ubatch-size 128`；
   - 变量 C：VLM 生成由整段改为**流式按短语增量播报**（`complete_stream` + 引擎按标点/长度切短语）。
   每次改动后用同一输入复测，记录采用/淘汰原因。
4. **真人短测**：目标板当前**没有麦克风与扬声器**（只有 HDMI 输出与 Tegra APE 采集），无法执行“真人开口/盒上听到”的验收；用 9 段真人录音（同一批素材，含 he/me/she 三位说话人）+ 真实 KWS/ASR/TTS/VLM 完成软件侧等价链路，并在文中明确标注“非真人现场”。

## 三、目标板实测数字（2026-11-11 22:16–22:19，单次采样）

### 3.1 整栈内存（cap = 4 GiB = 4,294,967,296 B）

测量口径：`tools/mem_probe.py` 依次加载 TTS/KWS/ASR/OCR/声纹/VLM/Scene 并做一次 OCR 价格问答 + 一次 VLM 文本 + 一次 VLM 单图请求；Python 进程取 `/proc/self/status` 的 VmRSS/VmHWM，llama-server 取 `/proc/<pid>/status` 的 VmHWM，两者相加。

| 指标 | 实测 |
|---|---|
| Python 进程 RSS | 733.2 MiB |
| llama-server RSS | 3,266.2 MiB（含视觉编码器分配） |
| **整栈合计** | **3.906 GiB** |
| **整栈峰值** | **3.906 GiB** |
| 判定 | **≤ 4 GiB（通过）**；距上限余量约 95 MiB |
| 常态 1.5–2 GiB 目标 | **未达到**（3.9 GiB，主因模型 + 视觉投影 + CUDA 计算缓冲约 1.95 GB + 3.2 GB 进程） |

分阶段 RSS：baseline 29.0 → TTS 35.6 → KWS 156.1 → ASR 192.4 → OCR 488.6 → 声纹 609.9 → scene 645.7 → 含 VLM 图片 733.2 MiB。

## 六、已知问题与误判/漏拒样本

1. **常态 1.5–2 GiB 未达到**：整栈 3.9 GiB，主要被模型/proj/CUDA 缓冲占满；如需压到 2 GiB 需更小模型或 CPU-only 部分层（需重新评估时延）。
2. **KWS 两字唤醒偶发漏检**：Piper 合成音声学不稳定导致；真实用户语音待现场；阶段 7 调参候选（阈值/关键词分数/尾部 blank）。
3. **相机暗光**：现场画面 blurry+dark，走质量降级回答“看不清”，未在正常光照下验证（无现场）。
4. **ASR 对短指令/合成音漂移**：出现过“继续”被截断、“哪个贵”识别成“拿个贵”；已通过词表与固定音频夹具缓解，真人语音待现场。
5. **合同真实主控并行**未验证（见 3.6）。
6. **VLM 小字密集可能漏行**：金额/日期一律以 OCR 为准的设计已固化。
7. 视觉请求会临时抬高 llama-server RSS（单图 2,367 ms 首请求时含分配），已计入峰值测量。
